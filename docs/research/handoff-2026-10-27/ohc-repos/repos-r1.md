### Top findings for Sahara
1. **Patients can log in by OTP.** `api/v1/otp/send` → `otp/login` → patient JWT → `otp/patient` and slots/appointments (care_api_backup `OTP/`). A Sahara family app could use this, but only against each hospital's own CARE server. That needs the hospital to allow it, and to have SMS switched on (care_clinic ships with `USE_SMS=False`). This is not open data.
2. **No repo in this lane exposes patient data publicly.** Everything clinical needs a staff JWT or the patient's OTP JWT. Clinical data cannot be pulled without the hospital's permission. The only no-auth items are the plugin registry JSON and, apparently, the facility staff-booking lists. The `care` backend lane should confirm which endpoints really allow unauthenticated access.
3. **Pain body map:** care_dental_fe is an MIT, well-tested model for a body-region question type (https://github.com/ohcnetwork/care_dental_fe, `SCHEMA.md`, `src/manifest.tsx`).
4. **Palliative metrics:** care_analytics_sql has real queries for deployments that look palliative: mobility status, comfort-device and patient-care referrals, Pallium medication dispense/returns. It has no licence, so use it as reference only and ask OHC before copying.
5. **Voice to form:** care_eka_scribe_fe shows how to turn recorded speech into form fields. Sahara should use the pattern with its own server issuing tokens, not ship a key in the app.
6. **Safe test setup:** care_create plus care_demo_facility_setup seed packs give a local CARE with synthetic patients and questionnaires to build against.
7. **Security patterns to avoid:** browser-held OpenAI keys sent along with PHI (care_ask_fe), build-time vendor tokens (eka_scribe), and committed demo credentials and old JWTs with a phone number (care_api_backup `environments/`, `OTP/*.bru`). Consider telling OHC about the committed passwords for `care-api.do.ohc.network`.
8. **Licences:** six repos have an MIT LICENSE file: analytics_fe, api_backup, clinic, demo_facility_setup, dental_fe and eka_scribe_fe. Five say MIT or ISC only in package.json. care_analytics_sql and care_be_plug_config_generator have no licence, so ask OHC.

Confidence: high for repo contents and licences. Moderate for what the `_kc` and `_pallium` suffixes mean, and for whether the two `auth: none` facility endpoints are really public on the server; the latter needs checking in the `care` backend lane.
