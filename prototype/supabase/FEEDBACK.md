# Feedback intake

The website has two distinct, voluntary forms: app feedback at `/feedback`, and the dedicated hospital survey at `/hospital-survery`. The older `/feedback?form=hospital` link and `/hospital-survey` spelling redirect to that dedicated survey. The survey has no app-feedback switch. App feedback is not a clinical report. The directory survey collects professional name/registration and optional professional follow-up contacts separately from hospital details. No patient information or attachments are requested. Both forms store consent and server-forced form/consent versions. Hospital submissions remain **pending review**; this feature does not verify clinicians, publish listings or update a map.

### Optional professional follow-up contacts

The contact-aware hospital form offers optional professional mobile/email, privately stored only in `sahara_hospital_contributors`. Do not enter patient or family contact details. Empty optional values become database NULL. Mobile is normalized to ten Indian digits starting 6–9 (spaces, parentheses, hyphens and an optional `+91` are accepted); email is trimmed and checked for conventional ASCII mailbox/domain syntax. Neither format validation nor storage verifies identity or deliverability, and no OTP, SMS, email or marketing message is sent.

Additive migration `20261019102414_sahara_hospital_optional_contacts.sql` must precede the compatible Edge update. Existing hospital payloads with neither contact key retain V1 form/consent versions and their exact canonical content hashes. New payloads supply both keys (even when blank), use V2 form/consent versions, and exclude both fields from facility JSON. A mixed one-key shape is rejected. No existing row, historical consent or receipt hash is rewritten. The original intake migration remains immutable. Deploy database first, then the V1+V2 Edge validator, then enable the contact-aware UI; failures must never be shown as saved.

This additive migration and Edge version 2 were verified on 19 October 2026. A synthetic V1 receipt created before migration replayed afterward with its exact stored hash and V1 consent unchanged. V2 formatted contacts normalized to the private contributor columns; blank contacts became SQL NULL, and facility JSON contained neither contact field. Retry/conflict, invalid/mixed contact shapes and unchanged app-feedback submissions passed. Anonymous/authenticated table, column and function access remained denied; advisors had no change from the preceding intake review. Four labelled synthetic compatibility records were removed with exact-ID/label guards, returning row counts and legacy-column integrity hashes to the pre-change baseline. No real contact data or email/SMS/OTP service was used.

## Deployment boundary

Project: `cghlkqeqiokjqdionrkc`, matching `app/android-account/account-auth.ts`. Never point this feature at the old transcription project. Deploy only the new `sahara-feedback` function with `verify_jwt=false`: public, nonmedical intake is intentional. The function uses the platform-provided `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` internally. No service credential, proxy secret or user sign-in is needed in the website/browser. The Next `/api/feedback` proxy targets this exact project/function; the Edge function rejects another project configuration.

Migration `migrations/20261019095122_sahara_feedback_intake.sql` creates four isolated RLS tables and two invoker functions. Public, anonymous and authenticated roles receive no table privileges or function execution. Service-role intake uses only the submit RPC; all essential validation is repeated at Edge and database. No public views or read/update/delete API is supplied.

## Abuse and retry behavior

Edge limits JSON to 12,000 bytes and enforces exact schemas, enums, required consent, conditional Other/state/supply fields and mutually exclusive services. Both forms share an atomic rolling 24-hour cap of 100 receipts, 5 per opaque client token, and 60 seconds between new receipts per token. The database serializes quota checking and insertion across replicas. Retrying an identical UUID/payload returns its existing receipt; changing its payload returns conflict. Rejected submissions do not allocate receipt rows. A browser cookie is HttpOnly and SameSite=Strict; only its HMAC is persisted, never the raw token or IP address. The shared global cap bounds rotating-token abuse, but can itself be exhausted by an attacker. This is **not spam-proof**: add a server-verified CAPTCHA before broader public rollout. Origin checks and the honeypot are supplemental, not security boundaries for the deliberately public Edge endpoint.

No request bodies, names, registration numbers, raw IPs or credentials are logged by the feature code. Hosting/Supabase infrastructure may keep its own service logs. Restricted database administration can access submissions. Automated retention, a review administration screen and a self-service deletion workflow are not implemented; do not promise these or imply that an entry is already verified. Decide retention and operational review responsibilities before broader collection.
